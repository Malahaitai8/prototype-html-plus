# 测试目标

验证 Step 3 通用线框稿能力：它应根据不同 PRD / 产品场景生成不同结构的低保真 HTML，而不是套用固定业务模板。

# 测试输入

请用 `$prototype-html-plus` 测试三个场景。前两个场景用于验证“已确认 PRD Lite 后直接生成线框稿”，第三个场景用于从需求挖掘一路测到线框稿生成。

## 场景 1：B 端数据更新看板

```text
Use $prototype-html-plus.

基于已确认 PRD Lite，生成“数据更新看板”的 Step A 线框稿。
当前步骤只做主路径：新增数据、更新数据、全球摄像头、数据更新明细。
要求：B 端桌面 Web、结构线框、包含右侧说明文档、编号圆点标注、Tab/筛选/详情交互。
```

## 场景 2：C 端 AI 健身监督 App

```text
Use $prototype-html-plus.

基于已确认 PRD Lite，生成“AI 健身监督 App”的 Step A 线框稿。
当前步骤只做主路径：今日计划首页、训练打卡、宠物状态反馈。
要求：C 端 iOS App、移动端线框、包含右侧说明文档、编号圆点标注、状态切换/详情交互。
```

## 场景 3：全新端到端测试 - 社区闲置交换小程序

这个场景不是 demo 业务，目的是验证 Skill 能从模糊想法开始，先做 PRD Lite，再按用户确认进入当前步骤线框稿。

### 第 1 轮输入

```text
Use $prototype-html-plus.

我想做一个社区闲置物品交换小程序，邻居可以发布闲置、交换或低价转让，最好有可信身份、预约自提和纠纷处理。先别写代码，帮我梳理需求。
```

### 第 1 轮预期

- 不生成 HTML。
- 输出 PRD Lite 草案。
- 标出已确认 / 待确认 / Agent 假设。
- 提问不超过 5 个阻塞问题。
- 需要确认平台、用户角色、第一版范围、线框 / 高保真、信任与交易边界、分步计划。

### 第 2 轮输入示例

```text
平台做微信小程序；第一版做线框稿；优先做发布闲置、浏览列表、发起交换预约三个动作；用户是同小区住户；只做邻里自提，不做快递和在线支付；设计原则是轻量、可信、避免陌生人压力；风险边界是不要承诺平台担保，不鼓励私下大额交易，纠纷处理只做记录和引导。请更新完整 PRD Lite 给我确认，先不要生成 HTML。
```

### 第 2 轮预期

- 回显完整更新后的 PRD Lite。
- 当前步骤应收敛为 Step A：发布闲置 + 浏览列表 + 发起交换预约。
- 设计参考应路由到 C 端微信小程序 / WeUI 方向，而不是套用 B 端表格或 AI 健身 App 卡片。
- 继续要求用户确认是否保存需求、是否进入 Step A。

### 第 3 轮输入示例

```text
确认 PRD，不保存 requirements.md。请只生成 Step A 线框稿 HTML，做完后给我预览方式、测试方式、修改文件和下一步建议，先不要继续 Step B。
```

### 第 3 轮预期

- 生成可预览 HTML 线框稿。
- 结构应符合社区交换小程序：发布入口、闲置列表、物品详情 / 预约交换、身份 / 小区可信提示、纠纷记录入口或说明。
- 仍保持低保真，不做品牌视觉和真实图片。
- 包含右侧说明文档、编号圆点、标注显隐、双向 hover 高亮。
- 至少包含一个适配该业务的交互，例如分类筛选、发布表单展开、选择物品详情、预约状态切换。
- 完成后停止，等待用户验收。

# 预期行为

- 先确认已有 PRD Lite 和当前步骤，不应重新发散需求。
- 只生成当前步骤，不做完整产品。
- B 端示例应偏桌面结构线框：指标、筛选、表格/明细、详情。
- C 端示例应偏移动流程线框：卡片、主行动按钮、宠物状态、打卡反馈。
- 全新场景应根据需求选择结构和参考方向，不应复用 demo 业务文案或固定布局。
- 微信小程序 / 社区交易类需求应体现移动小程序、列表 / 发布 / 预约 / 信任提示等结构，而不是强行套表格或健身状态页。
- 如果用户要求单屏移动原型，应使用一个可交互容器承载当前步骤需求；不能为了单屏丢掉已确认需求。
- 如果单屏无法覆盖，应先建议拆成 Step A1 / Step A2，并说明哪些需求分别进入哪个子步骤。
- 两者都必须包含右侧说明文档和编号圆点标注。
- 两者都不能使用 SVG 长连线。

# 预期产物

- 可预览 HTML 线框稿。
- 右侧说明区包含原型说明、功能说明、字段说明、交互说明、验收点。
- 4-6 个编号圆点标注。
- 标注显隐和双向 hover 高亮。
- 至少一个基础交互：Tab、筛选、展开/详情、状态切换之一。

# 人工验收点

- Skill 没有把示例 demo 当成固定业务模板。
- 页面仍然是低保真线框稿，没有滑向高保真视觉。
- 没有外部 CDN / 远程资源依赖。
- 每次只做 PRD 分步计划中的当前步骤。
- 风格和结构来自具体 PRD、平台和设计参考路由，而不是所有产品都长成同一种模板。
- 移动 / 小程序原型的呈现方式清楚：多屏流程总览或单屏可交互容器；无论哪种都保留当前步骤需求覆盖。
- 多轮微调后仍能守住 Skill 基线：当前步骤、已确认需求、右侧说明、编号圆点、本地预览、用户验收。
- 完成后要求用户验收，再进入下一步。

# 失败表现

- 不看 PRD 当前步骤，一次性生成完整产品。
- B 端和 C 端输出结构高度雷同。
- 套用了 demo 的业务文案或模块。
- 对新场景仍套用数据看板或 AI 健身 App 的结构。
- 不根据平台 / 端型选择参考方向，或一次性加载所有参考导致输出发散。
- 用户要求单屏后，遗漏上一轮 PRD 已确认的任务、字段、状态或风险边界。
- 多轮修改后忘记 Skill 规则，例如删掉右侧说明、编号圆点、验收说明，或未经确认扩大 / 缩小当前步骤。
- 使用长连线或复杂视觉装饰。
- 没有右侧说明文档或编号标注。
- 未经用户验收直接继续下一步。
